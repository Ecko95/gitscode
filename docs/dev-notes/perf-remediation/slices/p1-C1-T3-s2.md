**Summary:** `readBudgetUsage` no longer calls `getSnapshot()` (10 `findAll` + full `decodeReadModel` + repo
identity resolution). It now issues a single kind-filtered query on one table and reuses the identical JS
reduction, so budget numbers are byte-equal to the snapshot-derived values on the same data. A 60s `Ref` memo
caps how often even that query runs. Combined with s1's gate hoist, the budget path is off the 5s steady-state
tick entirely.

**Ponytail shortcuts:** reduce in JS rather than a pure-SQL `SUM(per-thread MAX)` aggregate — deliberate, to
avoid replicating the JS number semantics (non-negative/finite/integer, `totalProcessedTokens`-else-`usedTokens`,
contributing-only `updatedAt`) in SQL/JSON where a subtle mismatch would corrupt billing/limits accounting. The
kind filter already cuts row volume to the two relevant kinds; the per-thread reduction is cheap and provably
equivalent. Marked with `ponytail:` in-file.

**Overshoot bound (invariant):** the 60s memo means an automode budget check can read usage up to one 60s window
stale, so automode can overshoot `maxBudgetUsd` by at most one 60s window of spend before the next refresh. TTL
constant `USAGE_MEMO_TTL_MS` documents the ceiling; tighten if a hard cap ever needs it.

**Residual risks:** none functional. The memo caches only successful reads (query failure propagates and is
caught upstream into `unavailable`, same as before), so a transient DB error does not poison the cache.
